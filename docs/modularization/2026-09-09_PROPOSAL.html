00Executive Summary

4

0

0
Cycles

go-taskqueue is a single-module repo with 19 packages and a clean package-level DAG. The five packages that constitute the embeddable library core — task, journal, queue, executor, worker — each pass the Unix one-sentence test and compose like pipes; they become sub-modules with hard go.mod boundaries. The application layer (CLI, web UI, harvest, sweepers, bridges, budget, consumer, runactor, e2e) stays in the root module: it co-changes constantly and has no independent consumer. Because every import path is unchanged (module paths stay github.com/larsartmann/go-taskqueue/internal/…), the entire migration is go.mod plumbing plus CI/build wiring — no source file moves, no API change, and the “internal/ until the API stabilizes” stance (ADR-0001/0002) is preserved exactly.

What this buys

Compile-time enforcement of the layer DAG (a worker→webui or queue→harvest edge can never be added again), per-module GOWORK=off build/test isolation in CI, stdlib-only domain modules that future external consumers can import if/when paths are promoted, and faster focused iteration for the multi-agent workflow this repo runs.

04DAG Verification

Verified mechanically: for each candidate module, production and test imports were enumerated with go list -f (Imports, TestImports, XTestImports). Every edge points strictly downward; no candidate imports any root-module package, so the root→module direction cannot form a cycle:

root (app) → worker → {queue, executor} → {task, journal}
queue → journal, task  ·  executor → task  ·  task, journal → (leaves)

Cycle-proofing going forward

After the split, the compiler owns this property: a queue import of internal/worker becomes an unresolved module dependency (missing require/replace), not a silent new edge. The per-module GOWORK=off CI gate enforces that each module’s go.mod lists exactly what it uses.

05Replace / Workspace Strategy

Deviation from the skill default: replace-only, no go.work

The skill recommends the dual go.work + replace strategy. This repo deviates deliberately: the buildflow-managed .gitignore explicitly excludes go.work / go.work.sum, and replace directives alone fully determine resolution for root and every sub-module. With replace-only there is no go.work/replace drift to police (skill FM#4 eliminated by construction), no go work sync idempotency gate, and nix/CI builds are identical to developer builds. Local developers may still create a private go.work if they want; it changes nothing because replace wins resolution.

Rules applied to every go.mod:

RuleValue
Internal requirespinned v0.0.0 (no pseudo-version churn)
Internal replacesrelative paths (=> ../task), never absolute — portability audit in CI
Transitive siblingseach module requires every sibling it imports directly or transitively (worker also requires journal for its tests)
go directivego 1.26.7 in every module (matches toolchain; jsonv2 experiment only affects root via go-sse)

Mock/double placement: no production-package mocks were found in the five core packages; doubles live in _test.go. White-box tests stay in their packages, stdlib testing only (repo convention: table-driven, plain testing) — no test framework dep enters any go.mod.

Error type placement

Sentinel errors live in internal/task/errors.go — the module that defines the Task/Status contract. Every producer and consumer already imports task, so errors.Is works across every boundary with no new placement. journal defines its own fact types and has none. Implementation-specific errors (sqlite/pgx) stay inside queue. No Option-B errors module needed — Option A (errors with their interface) falls out of the existing layout.

10Migration Plan (Pareto tiers)

Each step is one commit, leaves the tree green (build + vet + -race tests), and is independently revertable. Order = dependency order (leaves first), which is also Pareto order: the leaves unlock the most boundary value.

go.mod + root require/replace; full gate; commit.

Tier 1 — extract internal/journal (leaf, stdlib-only)

Same shape as step 1.
