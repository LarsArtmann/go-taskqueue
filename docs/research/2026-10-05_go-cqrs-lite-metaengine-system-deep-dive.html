00Summary

The migration is real and the read side is adopted the right way — planned tables with columnar layout and declarative pushdown, not the naive JSON-blob path — and every go-cqrs-lite module is pinned at its latest tag. But the owner’s directive is only about 60% realized. The projection’s delivery machinery (cursor durability, catch-up, poison handling) is hand-rolled where the library ships projectionhost with durable checkpoints and a dead-letter queue; and the product’s hottest read (status tallies) bypasses metaengine’s O(1) Delta aggregates in favor of a full-table scan plus a Go loop. system.New runs with an empty DomainConfig — a justified deviation (no second journal), but it means system contributes only engine lifetime and close ordering today.

The bottom line Two findings carry most of the value: (1) the readmodel’s in-process cursor forces a full-journal replay on every process start — measured 9,523 facts on the production dogfood journal — and a single malformed fact detail can wedge the projection forever with no DLQ; the library’s projectionhost exists precisely for this and the in-repo FactJournal adapter already implements its required interface. (2) P5’s planned “dual tally collapse” should collapse ONTO metaengine Delta counter queries — the upstream cookbook’s first pattern is literally a status-count dashboard.

01Current usage

go-taskqueue imports eleven go-cqrs-lite module paths across five internal packages. The queue stores ride the upstream queue/ engine family (S1 thin drivers); the read model is a metaengine Store over a dedicated SQLite projection file; the composition root wraps a system.System around that same file’s engine lifetime.

tq runtime internal/queue/{sqlite,postgres} ── thin drivers over queue/{sqlite,postgres}/v4 (S1) internal/queue/{sqlitev4,postgresv4} ── queue/v4 Store contract, facts bridge (S1) internal/readmodel ── metaengine/v4 + sqliteengine/v4 Store, Plan (S3) internal/composition ── system/v4 New(DomainConfig{}, Deployment) (S4 shell) internal/journal/cqrs ── event.Journal + event.SeekableJournal adapter (ADR-0014) cmd/tq ── readmodel.Open + CatchUp per invocation

Consumption sites: internal/readmodel (metaengine Store, Plan, TypedReader, Watcher, ServeSSE — model.go, queries.go), one system import (internal/composition/compose.go), the queue engine adapters (internal/queue/sqlitev4/adapter.go, postgresv4/adapter.go over queue/v4), and the read-only journal bridge (internal/journal/cqrs/journal.go). CLI surfaces opt into the projection via --read-model (default ON since P2): tq stats, tq api, tq serve (cmd/tq/main.go:1711, 3165, 3252).

◆What’s already excellent

+
Planned tables via the advanced path tasksQuery = Query[TaskList, TaskRow] with OnRecordTyped folds, FilterOnField/SortOnField declarative pushdown, WithColumnarLayout — every TaskRow field is a typed SQL column (internal/readmodel/queries.go:38–112). This is the v5-recommended surface, not the deprecated tiers.
+
Watcher + ServeSSE as the live mechanism metaengine.NewWatcher with replay ring (1024), heartbeat, timeout; EventsHandler wraps ServeSSE with Last-Event-ID reconnection (internal/readmodel/model.go:120–123, 289–303). This is the sanctioned replacement for the ADR-0003 hand tailer that P5 deletes.
+
TypedReader with the documented typed-nil avoidance Reads go through NewReader[TaskRow].Scan with conditional WithFilter options; the query-input dispatch pitfall (nil *string binds as = NULL) is documented and dodged (queries.go:23–30, model.go:230–257).
+
Durable projection file, planner-satisfying sqliteengine at <db>.readmodel.db with WAL + busy_timeout; the projection is disposable and rebuildable by design (model.go:41–46, 86–105).
+
The bridge already exists journal/cqrs.FactJournal implements event.Journal AND event.SeekableJournal over any queue store, with the dangling-cursor contract handled (journal.go:31–34, 76–94) — the exact interface projectionhost consumes. Adoption finding #1 needs no new adapter.
+
Version discipline Every pinned go-cqrs-lite module equals its latest tag, verified today against the upstream checkout (metaengine v4.16.0, sqliteengine v4.5.0, system v4.10.1, queue family v4.0.1, record v4.6.1, dedup v4.2.3, claiming v4.0.1).

02Findings

Ordered by impact. Statuses: Missed Opportunity / Partially Used / Fully Leveraged.

Missed Opportunity · High impact

1. Projection delivery machinery hand-rolled — projectionhost + durable checkpoints unused

internal/readmodel/model.go:63,142–200 (atomic cursor, Run/CatchUp pump) · internal/readmodel/events.go:213–215, 247–249 (poison paths) · vs upstream projectionhost (crash-restart, checkpoints, DLQ, lag)

What the library offers: projectionhost.New(journal, checkpointStore) wraps journal reads, projection handlers, checkpoint persistence (“survives restarts, no event loss”), a dead-letter queue for poison records (“captured, checkpoint advances”), crash auto-restart with backoff, and Status()/LagPerProjection() for operators (projectionhost/README.md:13–22). system persists checkpoints as a metaengine Map collection on the declared engine (system/checkpoint_engine.go, ADR-0142).

What the project does instead: the Model keeps its cursor in an atomic.Int64 — “a restarted model replays the journal from the beginning” (model.go:139–141). The production dogfood journal holds 9,523 facts / 805 tasks (measured read-only today), so every readmodel-enabled process start — each tq stats, each tq api boot, each serve restart — re-reads and re-applies the entire journal, upserting 9.5k rows into the projection file; the projection WAL (4.2 MB) is already larger than its main DB (3.66 MB). Worse: a malformed task.enqueued detail (once the store row is compacted away) or a malformed reprioritized detail returns an error that freezes the cursor — the CLI fails and the serve pump retries the same fact every 500ms forever, with no DLQ and no restart budget. The plan’s own P4 text said “readmodel’s projector cursor moves onto the system checkpoint store” — that half never landed.

Recommendation Two-step adoption. Minimal (a day): persist the cursor through the queue’s existing watermarks table (internal/watermark already provides durable checkpoint-after-batch semantics for the sweepers). Full (the library shape): run the projection under projectionhost, feeding it the already-implemented FactJournal; checkpoints, DLQ, backoff and lag come from the library and the hand pump shrinks to a projection Handle. 
// Today: hand pump, in-process cursor (model.go)
cursor atomic.Int64            // lost on restart -> full replay
for { facts := src.Facts(ctx, cursor, batch); apply each; cursor.Store(last.Seq) }

// Target: the library owns delivery (projectionadapter is its canonical bridge)
journal := cqrs.NewFactJournal(store)          // already event.SeekableJournal
host, _ := projectionhost.New(journal, cpStore,
    projectionhost.WithDeadLetterStore(dlq, 3),
    projectionhost.WithCheckpointEvery(500))
// projection Handle: eventFor(fact) -> store.ApplyRecord  (existing code)
Missed Opportunity · High impact

2. Status tallies bypass metaengine Delta aggregates — full scan + Go loop

internal/readmodel/model.go:259–272 (StatusCounts → unbounded Tasks scan) · cmd/tq/main.go:2043–2075 (tallyStats / tallyModelRows dual paths) · vs metaengine COOKBOOK §Counter Patterns / “Status Count Dashboard”

What the library offers: counter queries fold metaengine.Delta maps — O(1) point reads, O(groups) for per-key groups. The cookbook’s FIRST pattern is a status-count dashboard; the second is a per-key counter (rate limiter). This is precisely tq’s by_status / by_project read.

What the project does instead: StatusCounts calls Tasks(ctx, TaskFilter{}) — a WithLimit(0) unbounded planned-table scan materializing every TaskRow into Go — then counts with counts[r.Status]++. The CLI keeps two parallel tally implementations (tallyStats over store rows, tallyModelRows over projection rows) — the exact split brain P5’s “dual tally collapse” item exists to remove. Every dashboard load and every /api/stats request pays O(n) for an O(1)-capable read, compounding finding #1 (replay, then full scan).

Recommendation Declare one Delta counter collection keyed “status” and one keyed “project|status”, folded from the same facts (OnRecordTyped handlers already exist as evtClaimed/evtCompleted/…); read via metaengine.ExecuteTyped. Collapse BOTH CLI tallies onto it — P5’s dual-tally deletion then lands on the library’s aggregate surface instead of a third hand-rolled path. 
// Today (model.go:260) - O(n) scan + Go tally
rows, _ := m.Tasks(ctx, TaskFilter{})       // unbounded, all rows to Go
counts := map[string]int{}
for _, r := range rows { counts[r.Status]++ }

// Target - the cookbook's first pattern, O(1) (absolute deltas, same typed fold inputs)
statusCounts := metaengine.Query[countInput, map[string]int64]("status_counts",
    metaengine.On(evtEnqueued{}, func(e evtEnqueued) metaengine.Delta {
        return metaengine.Delta{"pending": +1}
    }),
    metaengine.On(evtClaimed{}, func(e evtClaimed) metaengine.Delta {
        return metaengine.Delta{"pending": -1, "running": +1}
    }),
    // ... one On per lifecycle fact, same evt structs events.go already defines
)
counts, _ := metaengine.ExecuteTyped[countInput, map[string]int64](ctx, m.store, countInput{})
Missed Opportunity · Medium impact

3. Platform health invisible: system.Health / metaengine Doctor unused by tq doctor and /health

internal/composition/compose.go (System built, health never queried) · zero HealthCheck references in internal/ (rg) · vs system README §Health Check (Detailed), metaengine store.Doctor, projectionhost Status()

The System exposes HealthCheckDetailed (per-engine status including failed projection workers), metaengine exposes Doctor(ctx) and engine stats, projectionhost exposes per-worker status and lag. None of it is surfaced: tq doctor inspects repos and gates but never asks the platform whether the projection engine is alive or how far behind the journal cursor is (HeadSeq − JournalCursor). A wedged projection (finding #1) would be operationally silent — the same “nothing noticed flake check was never green” failure class, but in production tooling.

Recommendation Add a projection section to tq doctor (engine stats, cursor lag, checkpoint state) and fold HealthCheckDetailed into the existing token-gated /health surface. Cheap, and it turns findings #1/#2 regressions into visible signals.
Partially Used · Architectural (justified — read the nuance)

4. system.New runs with an empty DomainConfig — a lifecycle shell

internal/composition/compose.go:57 · plan doc P4 (“collections declared as system projections where the feed maps 1:1; cursor onto system checkpoint store”)

The landed S4 root declares RoleProjections over the projection-home engine but registers zero projections, zero deciders, zero queries — system contributes engine lifetime and GracefulClose ordering only. The honest nuance: this is a justified deviation, not an oversight. system’s projection feed sources from its EventAdapter, which reads a metaengine backend journal (system/adapter_event_journal.go) — declaring the tq collections as system projections would require mirroring the queue journal into that engine journal: a second source of truth, which the archived composition map §3 and the endgame plan explicitly forbid. The queue engine journal IS the journal (P3).

What is genuinely unfinished is the plan’s other half — the durable cursor (finding #1) — plus the health surface (finding #3). The strategic question for the platform relationship: ask upstream whether system’s event adapter can accept an external event.SeekableJournal as its source. If yes, tq could declare its collections as true system projections (system.RawQuery(tasksQuery)) with no journal duplication, and the composition root stops being a shell. Until then, projectionhost (finding #1) is the sanctioned library shape for exactly this topology.

Recommendation Keep the shell, finish its obligations (checkpoints via #1, health via #3), and file the upstream conversation (external SeekableJournal as system projection source). Revisit declaring DomainConfig projections only if upstream adopts the adapter seam.
Missed Opportunity · Medium impact

5. Unbounded reads — cursor pagination unused

internal/readmodel/model.go:240 (WithLimit(0) // unbounded: the caller paginates)

metaengine ships serialized cursor pagination (README §Pagination + Cursor Serialization; COOKBOOK §Cursor Pagination). The Model deliberately reads everything and lets callers page in memory. At 805 tasks that is fine; the journal grows monotonically and every board/table render pays full materialization. With #2 landing, only the row-rich views need this — adopt cursors there.

Recommendation Expose the TypedReader cursor (WithLimit + cursor round-trip) through the dashboard’s table fragment; keep unbounded reads only for export paths that genuinely want everything.
Missed Opportunity · Low impact

6. Observability seams idle: hooks, MetricsRecorder, ApplyEncoded

internal/readmodel/model.go:160 (slog only) · metaengine README §Observability, §ApplyEncoded · projectionhost WithMetrics

The pump logs errors via slog; metaengine’s MetricsRecorder hooks, projectionhost’s WithMetrics, and the ApplyEncoded zero-copy hot path (its canonical consumer is projectionadapter — which finding #1 adopts anyway) are unused. Small wins that mostly arrive for free with #1.

Partially Used · Low impact

7. Engine-swap claim unexercised; postgres facade consumers have no readmodel story

internal/composition/compose.go:41–55 (hardcoded sqlite DSN) · metaengine pgengine exists

The compose.go why-comment sells “swap sqlite → postgres by editing Engines” — true by construction, never exercised by any test. And the public facades (ADR-0016) re-export the queue stores only: external postgres consumers get no projection surface at all (readmodel is internal + root). Not urgent — tq’s CLI is sqlite-only — but P5’s docs truth pass should say it out loud instead of implying platform parity.

Observation · feeds an open owner decision

8. Three journal-tailing implementations until P5 — converge on one

internal/webui tailer (ADR-0003, P5 deletes it) · internal/consumer (ADR-0009, ghost — existing BLOCKED owner row) · internal/readmodel pump

Until P5 lands, three independent mechanisms page the same fact journal. P5 removes the hand tailer; the endgame should then leave exactly one: the projectionhost-based pump from finding #1. That also answers the existing owner-blocked TODO row about internal/consumer’s fate — if the readmodel ride projectionhost, the consumer dispatcher’s remaining justification evaporates unless a push-notify seam (ADR-0009 D4 v2) is wanted for it. Worth deciding in the same breath as P5 cadence.

05Conclusion

Adoption is genuine on the read side and exactly where it is hardest to fake (planned tables, typed pushdown, watcher/SSE), version discipline is perfect, and there are no anti-patterns — the engineering that exists is sound. The gap is concentrated and structural: the projection’s operational machinery (durability, poison handling, health) was rebuilt by hand inside readmodel instead of taken from projectionhost/system, and the aggregate read path ignores the module’s flagship counter pattern. Both top fixes deepen usage of the two modules the owner named, both are small relative to P5’s already-planned deletions, and landing them before the P5 docs truth pass means the endgame ADR gets to describe the finished shape rather than the interim one.

Single next action Land opportunities 1+2 together as the P5 dual-tally collapse: Delta counters replace both tallies, and the cursor gains a durable home. Everything else on the list composes on top of that seam.
