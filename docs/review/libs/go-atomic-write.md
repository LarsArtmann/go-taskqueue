## 1. Where the need exists today

go-atomic-write offers: `Write`/`WriteWithPerm` (unique tmp + fsync + atomic rename + directory fsync on non-Windows), `WriteVerified` (adds an xxhash64 fingerprint + gofrs/flock TOCTOU check → `ErrConcurrentModification`), `WriteIfChanged`, `WriteFunc*` including the unreleased `WriteFuncWithPerm` (atomicwrite.go:17-179; staging stage.go:16-152; commit.go:20-76; fingerprint.go:26-46). Its Windows path retries the rename itself (5 attempts, 1 ms base doubling backoff, on `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`; rename_windows.go:13-47) — a path its own FEATURES.md rates "PARTIALLY_FUNCTIONAL … untested on real Windows hardware (build-tag compiles only)" (FEATURES.md:50; ROADMAP.md:15-16). Its README scores "DIY write + rename" as crash-durable "Partial" and not concurrent-safe (README:41-45), and its "When Not To Use" guide sets the boundary it is judged against here: the library "earns its keep under two conditions: the file is shared between processes (so concurrent writes are possible), or it must survive a crash (so torn writes matter)" (website/src/content/docs/guides/when-not-to-use.mdx:6-8, :50-53).

The tq code it would touch, as of HEAD — the replace-shaped surface is four implementations, not one:

- **Four hand-rolled tmp+rename implementations, six writes** (`rg -n 'os\.Rename\('` over non-vendor, non-test `*.go` → 4 call lines):
  1. **The worker-death marker** — `os.WriteFile(tmp)` then `retryx.RenameTransient(tmp, path)` (internal/readmodel/workerfailed.go:69-89; write :78, rename :82). The only implementation that retries.
  2. **`writeFileAtomic`** (cmd/tq/atomicwrite.go:11-25) — fixed `path+".tmp"` (:12), `os.WriteFile` (:14), bare `os.Rename` (:18), tmp removed if the rename fails (:19); doc: "a crash mid-write never leaves a torn final file" (:8-10). Call sites: the `$TQ_RESULT_FILE` verdict (cmd/tq/verdict.go:94, 0600), pool.conf (cmd/tq/bootstrap.go:758, 0600), the systemd unit (bootstrap.go:768, 0644) — commit 541ba86a.
  3. **The calibration-dataset trim** (internal/executor/calibration.go:194-243; tmp :230, write :232, rename :236) — landed 2026-11-13 (e7e10de4); called once per pool tick (cmd/tq/main.go:1681).
  4. **The failed-migration restore** (internal/queue/sqlitev4/migration/upgrade.go:224-249; whole snapshot read into RAM :228, write :235, rename :241) — commit ae906c25.
- **The deliberate seam**: `internal/retryx` is its own module (S4 root) — `RenameTransient(src, dst)` = 3 attempts, 50→100 ms, 2× multiplier, riding `go-retry`, tolerant of a missing source (rename.go:18-37). Package doc: "Each helper graduates here instead of growing a copy per module" (:6-7) — an explicit AGENTS.md-blessed seam (package table row `internal/retryx`), proven live by the 2026-10-25 Windows CI red on `TestConvergeProjectionHome` (:4-5).
- **Plain transient renames atomicwrite cannot express** (no temp-commit shape, no exported rename helper): projection-home snapshot-aside moves (internal/readmodel/schema.go:170) and depbump's go.work `.bak`/restore pair (internal/executor/depbump.go:588, :592).
- **The one read-modify-write site**: `ensureCrushConfig` reads `.crushrc`, strips its managed block, re-reads to short-circuit on byte-identical content, then writes plainly (cmd/tq/bootstrap.go:564-603; compare :591-593, write :599). That is `WriteIfChanged`'s compare half, hand-rolled without the atomic replace or the race check, on "operator-owned config the bootstrap only extends inside its managed block" (docs/architecture/io-surface/claims.cue:28-34).
- **Plain, non-atomic writes (11 `os.WriteFile` lines, non-test/non-vendor)**: four are the still-open INFO-class io-surface row (TODO_LIST.md:2054) — the `.tq-verify` pin ×2 (cmd/tq/bootstrap.go:537, :553), the `.crushrc` rewrite (:599), and the ask marker (cmd/tq/ask.go:236; the manifest classes it recoverable because "a corrupt marker parks the task permanently", claims.cue:62-67). The rest self-heal by contract: per-run agent logs (internal/executor/agent.go:469, :718), the verify-failure sidecar (internal/executor/sidecar.go:156), the effort cache ("a torn write self-heals as an unreadable cache", internal/harvest/effort.go:532-540), the session-registry rewrite ("torn lines are skipped", claims.cue:971-976; internal/session/registry.go:162), doctor's scratch probe (cmd/tq/doctor.go:2074, :2078).
- **Append-shaped writes (out of scope by design)**: calibration rows (internal/executor/calibration.go:93, :169), the session-registry ping line (internal/session/registry.go:81), RSS samples (cmd/tq/agentpool.go:1285-1286) — all `O_APPEND|O_CREATE|O_WRONLY`; the library's own guide routes append-only logs to `O_APPEND` (when-not-to-use.mdx:19-25).
- **Not file-backed at all**: `priority_scores` is a SQLite table (internal/queue/companion/schema.go:14, insert reads.go:342), watermark checkpoints are store writes (internal/watermark/watermark.go:50-63, :160-166), readmodel sidecars are SQLite DBs (internal/readmodel/dlq.go:62-89).

## 3. Findings (buy vs cost)

1. **Buy (real, and larger than on 11-11):** one call per site would close four gaps at once. `WriteWithPerm` gives fsync of the staged file (stage.go:88), directory fsync after the rename on non-Windows (rename_unix.go:17), a random-suffix staging name (stage.go:44-49) and the Windows rename retry (rename_windows.go:13-33); at HEAD only the marker gets any of these, and only the retry. The fixed staging name is the sharpest gap: the result file's contract is "the file's last write wins across work + close-out turns" (internal/executor/result.go:378-379), so two overlapping `tq verdict` calls in one run share `path.tmp`; the worst case per code is an empty published file, which `ReadVerdict` reports as "channel never materialized" (:384-397) and strict executors fail as a retryable attempt (:407-416).
2. **Why it still does not flip:** (a) by the library's own boundary none of the six writes qualifies — no site has two writing processes (the marker has the fold-lock-elected host; the result file has one run; pool.conf and the unit are "config files written once at deploy time", when-not-to-use.mdx:45-46; the trim runs on the single pool tick), and no site's loss "costs hours" (:52-53): a lost verdict fails the task's closeout (claims.cue:92-98), a lost trim costs calibration evidence (:414-419), pool.conf is re-rendered from the same flags; (b) the crash class the triage targeted is the process crash (cmd/tq/atomicwrite.go:8-10), which temp+rename already covers — fsync adds only against OS crash or power loss; (c) the Windows retry, the one gap tq has felt in production, is proven in-tree (rename.go:4-5; the test-windows CI job, .github/workflows/ci.yml:277) and not in the library (FEATURES.md:50), and no tq process holds a `writeFileAtomic` target open while it is written — the executor reads the verdict once, post-exit (result.go:384-389); (d) the unique name, the fsyncs and the retry are each a few stdlib lines inside `writeFileAtomic` (`os.CreateTemp` in the target directory, `Sync()` before the rename, `retryx.RenameTransient` for the rename — cmd/tq already requires retryx, cmd/tq/go.mod:85, and it is vendored at root), leaving the fingerprint-under-flock check as the library's only irreplaceable part, with `ensureCrushConfig` as its sole conceivable consumer.
3. **Cost (corrected):** +2 direct requires but only +1 new vendored module — `cespare/xxhash/v2 v2.3.0` is already an indirect require in four tq go.mods (root go.mod:13, cmd/tq/go.mod:37, internal/composition/go.mod:17, internal/readmodel/go.mod:26) and vendored; `gofrs/flock v0.13.1` appears in no go.mod and is not vendored (graph hashes in 7 sum files only). The four implementations live in four modules (cmd/tq, internal/executor, internal/queue/sqlitev4, internal/readmodel), so each adopting module takes the require.
4. **Cost (unchanged):** adoption does not subsume `retryx` — the library's Windows retry is private to its commit path, and 2 of 4 retryx call sites (schema.go:170 snapshot moves, depbump.go:588/:592 bak/restore) are plain renames atomicwrite cannot express. The result would still be two mechanisms for one failure class. tq-side observation, not a library argument: the duplication this report warned about already exists — four copies, one retrying, against retryx's own doctrine (rename.go:6-7) and an audit row that still names only two sites (TODO_LIST.md:1040).
5. **Migration trap if it ever happened:** `Write` gives a new file 0644 or copies an existing file's mode (stage.go:16-32), so the three 0600 sites must use `WriteWithPerm`. Adoption sites, in order of fit:

```go
// cmd/tq/bootstrap.go — ensureCrushConfig: replaces the compare + plain write (:591-601)
if _, err := atomicwrite.WriteIfChanged(path, []byte(out)); err != nil { // atomic + race-checked
	return false, err
}

// cmd/tq/atomicwrite.go — writeFileAtomic's body, if the stdlib route is declined
return atomicwrite.WriteWithPerm(path, data, perm) // fsync + unique tmp + Windows retry
```

## 4. Fit assessment

go-atomic-write is a good library aimed at config files and shared state exposed to competing writers, and it says so itself. tq now has the file shape it serves — six replace writes — but not the problem: its durable state lives in SQLite under a single-serialized-writer doctrine, and its file channels are single-writer, re-derivable, or explicitly lost-tail-tolerant. What changed since 11-11 is that tq chose to grow the shape by hand, four times, and that its own manifest now calls three of the writes durable and critical — which makes the helper's missing fsync and fixed staging name a legitimate engineering note rather than a non-issue. It is still not an adoption argument: the fix is local to a 15-line function, the one library capability with no stdlib equivalent (TOCTOU fingerprints under flock) has a single low-traffic consumer, and the library's Windows retry is less validated than the seam tq already runs.

## 6. Conclusion

Keep out. Re-litigated 2026-11-22 against `writeFileAtomic` and the two other new atomic sites: the library would add fsync durability, unique staging names, the Windows rename retry and TOCTOU checks that tq's helper lacks, but every one of tq's six replace writes sits inside the library's own "when not to use" boundary — one writer, loss measured in an attempt or a datapoint, not hours — and three of the four gaps are stdlib lines away. Revisit only on one of three triggers: a file acquires a second writing process; tq decides its three manifest-durable writes must survive power loss; or `ensureCrushConfig`-style rewrites of operator-owned files multiply. None is on ROADMAP.md (checked 2026-11-22: no row mentions atomic writes, fsync, or multi-writer files; its `.crushrc` rows at ROADMAP.md:200-208, :299 are managed-block content and guards, not write-safety).
