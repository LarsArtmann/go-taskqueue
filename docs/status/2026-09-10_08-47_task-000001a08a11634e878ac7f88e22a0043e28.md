## Summary

The CI lint step (advisory, `continue-on-error: true`) only ran
golangci-lint from the repo root, where `./...` never descends into nested
sub-modules (ADR-0011) — so all module-local findings (executor, worker,
queue backends, etc.) never surfaced in CI, while `ci-local.sh` had already
looped every module since the split. The fix appends the same
disk-derived module loop after the root run in the lint step's `run:` block,
preserving the step's advisory semantics (`|| true` per module inside a
step-level continue-on-error), with a comment explaining why the loop exists.

## e) WHAT WE SHOULD IMPROVE

1. **One shared script for the module loop.** The `find internal -name
   go.mod | sed ... | sort` loop is now copy-pasted in at least four places
   (ci.yml module gates, ci.yml govulncheck, ci.yml lint, ci-local.sh,
   AGENTS.md). A `scripts/for-each-module.sh` (exec a command per module)
   would make the fifth consumer trivial and rot-proof. Small, high-leverage.
2. **Verify-by-runner loop is slow.** Every workflow edit costs a full CI
   round trip to truly validate. A `actionlint` (or `nix run .#ci-lint`)
   devShell check for workflow syntax + shell semantics inside `run:` blocks
   would catch most of this class locally, instantly.
3. **Advisory step output is easy to miss.** Per-module lint failures print
   `== <module>` headers into an advisory step nobody reads on green runs.
   A one-line summary at the end ("modules linted: N, failing: [list]")
   would make the advisory signal scannable without changing gate semantics.
4. **Duplicated advisory baseline across modules.** Each sub-module gets its
   own `.golangci.yml`-resolution behavior; whether the root config actually
   applies inside sub-module directories should be checked once (golangci-lint
   v2 searches up-tree from the module dir, so it likely does — unverified).
   If any module silently runs with defaults, the per-module runs are
   louder but not comparable to the root's triaged baseline.
5. **TODO item 71 (measure CI time of module loops) gains urgency** with a
   third loop in the lint path; it was already queued, this work adds weight
   to executing it soon.
