   but the window still drifted into report-shaped work. A canonical
   "verification-only close-out" skeleton (verify → spot-check → loop-back →
   short report) would cut these windows to minutes and standardize §b3
   honesty about what was and wasn't re-run.
2. **Verification tiers should be explicit in close-outs**: existence
   (tracked) ≠ content (read it) ≠ behavior (ran it). This repo's reports
   increasingly claim "verified" without saying WHICH tier. I am as guilty
   as anyone — §a3 was tier-two work done late. Cheap fix: one line in the
   close-out template naming the tier per claim.
3. **The unharvested-§f gap is structural, not personal.** Three separate
   windows' §f items sat in reports only; TODO_LIST never saw them. Options:
   docs-health HARVEST as a mandatory step of every status task, or a gate
   that greps new reports for `- [ ]`-style §f bullets not present in
   TODO_LIST. Until then, every report is a leaky bucket.
4. **Evidence-class work should not depend on report prose for provenance.**
   The SHA256SUMS + tracked-files gate (both now filed) convert the 06-41
   §d1 near-miss and this window's content spot-check from heroics into
   mechanics.
5. **Stale re-dispatch needs a root-cause owner decision** (see §g1) —
   tally 8 and counting; the marginal cost of each duplicate is a full
   agent window plus a report.
