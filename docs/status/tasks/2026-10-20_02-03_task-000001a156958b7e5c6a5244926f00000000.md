1. **Commit latency vs the daemon:** the edit→commit gap is the only
   reason this session needed a heal at all. For small, well-scoped
   commits (this batch was two files + a tick), stage and commit BEFORE
   running any verification — the AGENTS.md edit→commit→battery ordering

2. **Fix-then-refactor ordering was inverted and cost a syntax detour:**
   I started the refactor (item 1) before the red-test fix (item 2),
   which lives in the SAME function being split. A partial-replacement
   edit left dangling body code (gopls flagged it, build caught it) and
   the fix had to be threaded through the new helper shape. Doing the
   two-line behavioral fix first, then refactoring, would have been one
   clean pass — though item-per-commit ordering would then need a
   temporary carry.
3. **The pin test under-specifies its own guarantee:** the row-626 test
   name promises the done-guard counts known, but the guarantee only
   holds at Every=1 (see b1). Pins should state their scope in the test
   comment or cover the Every>1 sibling — otherwise the next "it fails at
   Every=3" gets rediscovered from scratch.
4. **Static sentinels for control flow are a judgment call:**
   `errInFlight` turns a skip into an error the caller unwraps with
   `errors.Is`. It works and it keeps lastReportTime's signature
   `(time.Time, error)`, but `(time.Time, inFlight bool)` would be
   honest-er — sentinels invite misuse by future handlers that wrap or
   log them. Flagged for review, not changed post-commit.
5. **Root-wide vs in-module lint scoping (from d3):** the batch's verify
   habit should be "in-module golangci run, grep the classes I claim to
   have zeroed". Root runs answer a different question and nearly
   produced a false regression claim here.
