## a) FULLY DONE

1. **Diagnosis.** Root cause is NOT the sweeper and NOT the fixtures: it is
   `task.NewID` (internal/task/task.go). It minted
   `%016x(UnixMilli) + hex(10 crypto-random bytes)` — so two tasks created in
   the same millisecond got IDs whose lexicographic order was coin-flip. The
   sweeper's "oldest first" window sort (internal/status/sweep.go:242) sorts by
   `CompletedAt` (RFC3339, SECOND precision) with TaskID as the tiebreak — the
   tiebreak was random, so `TestSweepNthCompletionMintsOneReport`
   ("window order oldest first") and `TestSweepPinsCloseoutReportPaths`
   ("first entry report") flipped whenever fixtures landed in one ms. This
   adjudicates owner question §g1 of the 03-07 report: direction 1 wins —
   same-process IDs ARE creation-ordered by contract; the ID minting was
   wrong, the sweep tests were right. (The report's "ULID" name was a
   misnomer: the IDs are a homegrown ms-hex scheme, not oklog/ulid — that
   scheme exists separately in internal/journal/cqrs/seqid.go and is NOT
   affected.)
2. **Fix.** `NewID` is now process-monotonic: per-millisecond random seed
   (5 bytes) + zero-padded process-local monotonic sequence, mutex-guarded.
   Format unchanged: 36 hex chars. Lexicographic order = creation order,
   including within one millisecond. File: internal/task/task.go:15-46.
3. **Contract pinned.** `TestNewID` (internal/task/status_test.go) now asserts
   1000 consecutive `NewID()` calls are strictly increasing lexicographically,
   so the invariant can't silently regress.
