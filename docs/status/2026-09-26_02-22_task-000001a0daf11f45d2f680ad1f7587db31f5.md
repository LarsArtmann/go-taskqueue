## The dispatcher unsubscribe race (root-caused, fixed)

`unsub()` removed the subscriber from `d.subs` but an **in-flight
`drain`** held the stale pointer and kept reading facts with the
subscriber's cursor: the drain that delivered seq 1 can return from the
handler, advance the cursor to 1, loop, fetch the fact a test enqueued
AFTER `unsub()` returned, and invoke the handler again — a wide,
load-sensitive window that `-race` scheduling hits reliably (attempt 2,
single run under full-suite load). Not a test artifact: the pinned
contract (test name + the package's at-least-once doc) is "unsubscribe
stops delivery". The fix landed as daemon commit `c561ae25` (footerless
absorb — the known §d2 class).

Fix (internal/consumer/consumer.go): `subscriber` gains a `removed` flag
under its existing mutex; the unsubscribe closure sets it after slicing
the sub out; `drain` checks it before EVERY handler invocation and
returns. After `unsub()` returns, no new handler invocation can start (a
handler already running completes — documented on `Subscribe`).
